# Design: Elasticsearch 9.4.4 — secured 5-node cluster, hot/warm ILM, self-monitoring

- **Status:** Approved (2026-07-26)
- **Author:** paired session (Rurik + Claude)
- **Target deliverable:** public repo for the "Развернуть кластер Elasticsearch" homework

## 1. Goal

Deploy a fault-tolerant, secured Elasticsearch 9.4.4 cluster with Docker Compose, attach Kibana as the UI, configure an ILM policy with at least Hot + Warm tiers, and ship the stack's own component logs back into the cluster under the index name `self-monitoring`. OpenSearch is explicitly out of scope (user chose Elasticsearch).

## 2. Decisions (locked)

| Decision | Choice | Rationale |
|---|---|---|
| Deployment method | Docker Compose | Config files must be committed as deliverables; Elastic Cloud is managed and cannot produce them. |
| Topology | 5-node resilient (3 dedicated masters + 2 hot + 2 warm) | Tolerates loss of any single data node in either tier; user-selected. |
| Security | ON (TLS + auth) | Realistic, matches production; more impressive for grading. |
| Stack version | **9.4.4** (ES + Kibana + Filebeat pinned identical) | Current GA as of 2026-07-26; stack versions must match. |
| Log shipper | Standalone **Filebeat** 9.4.4 | Only Beats can write to a single custom fixed index name (`self-monitoring`); Elastic Agent forces data-stream naming. Beats supported through ~2027. |
| Cert generation | `elasticsearch-certutil` (pre-generated) | Transparent, reproducible, non-interactive `docker compose up`. |
| Filebeat auth | `elastic` superuser from `.env` (Fork A) | Simplest reproducible path; API-key script provided as optional bonus. |
| ILM placement | Tied to `self-monitoring` rollover alias (Fork B) | Component logs themselves demonstrate hot→warm→delete; one moving part. |

## 3. Topology & fault tolerance

Nine containers:

| Service | `node.roles` | Purpose | Heap |
|---|---|---|---|
| `es-master-1/2/3` | `[master]` | Dedicated master-eligible, quorum of 3 | 1 GB each |
| `es-hot-1/2` | `[data_hot, data_content, ingest]` | Hot tier | 1.5 GB each |
| `es-warm-1/2` | `[data_warm]` | Warm tier | 1.5 GB each |
| `kibana` | — | UI | default |
| `filebeat` | — | Log shipper | default |
| `setup` | — | One-shot bootstrap, exits 0 | — |

**Fault tolerance (rubric: "максимальный отказ — одна data-нода"):** 3 masters keep quorum after losing 1. Each data tier has 2 nodes with `number_of_replicas: 1`, so losing any single data node (hot *or* warm) keeps all shards available. Exceeds the rubric.

`discovery.seed_hosts` lists the 3 masters; `cluster.initial_master_nodes` lists the 3 masters (left in for fresh-deploy reproducibility, with a comment that it should be removed after the first successful formation in production).

## 4. Security model

- `xpack.security.enabled: true`, `xpack.security.enrollment.enabled: true`.
- Transport TLS: `verification_mode: certificate`, keystore + truststore `certs/transport.p12`.
- HTTP TLS: keystore `certs/http.p12`.
- `elastic` superuser password = `ELASTIC_PASSWORD` from `.env` (deterministic on first boot).
- Kibana authenticates as the built-in `kibana_system` user (the `elastic` superuser is disallowed for Kibana); password set by the `setup` service from `KIBANA_SYSTEM_PASSWORD`.
- Filebeat authenticates with the `elastic` credentials over HTTPS, trusting `ca.crt`.
- Cert material generated by `setup/generate-certs.sh` into `certs/`; `certs/` and runtime `data/` volumes are gitignored.

## 5. Bootstrap & startup order

Single `docker compose up -d` with no manual steps:

```
es-master/hot/warm  ──(cluster healthy)──▶  setup  ──(exit 0)──▶  kibana + filebeat
```

`setup` (`curlimages/curl`, mounts `ca.crt` + `.env`) waits for cluster green/yellow, then:

1. `elasticsearch-reset-password -u kibana_system -i -p "$KIBANA_SYSTEM_PASSWORD"` (via `docker exec es-master-1`, deterministic).
2. Creates ILM policy `self-monitoring-policy` (`PUT _ilm/policy/self-monitoring-policy`).
3. Creates index template `self-monitoring` matching `self-monitoring-*` with `index.lifecycle.name` + `rollover_alias`.
4. Bootstraps `self-monitoring-000001` with alias `self-monitoring` (`is_write_index: true`).

Kibana & Filebeat use `depends_on: { setup: { condition: service_completed_successfully } }`.

## 6. ILM + self-monitoring (tied)

- **Policy `self-monitoring-policy`** (`policies/self-monitoring-policy.json`):
  - `hot`: `rollover` (max_age `1d`, max_primary_shard_size `5gb`), `set_priority { priority: 100 }`.
  - `warm`: `min_age: 1d`, `set_priority { priority: 50 }`, `allocate { number_of_replicas: 1 }`, `forcemerge { max_num_segments: 1 }`. ES auto-sets `_tier_preference` so shards relocate to the `data_warm` nodes.
  - `delete`: `min_age: 7d`, `delete {}`.
- `self-monitoring` is a **rollover alias** (backing indices `self-monitoring-000001`, `-000002`, …). Filebeat writes to the alias; the current write index receives docs.
- **Exported JSON deliverable:** `policies/self-monitoring-policy.json` (also reproducible via `GET _ilm/policy/self-monitoring-policy`).
- Demo helpers documented in README: `POST self-monitoring/_rollover` and `POST <index>/_ilm/move` to force a tier transition for screenshots without waiting for `min_age`.

## 7. Filebeat log shipping

`filebeat/filebeat.yml`:
- `filebeat.autodiscover` with docker provider; templates match container images `elasticsearch` and `kibana` → collects all stack-component container logs.
- Processors: `add_docker_metadata`, `add_host_metadata`.
- `output.elasticsearch`: `hosts: ["https://es-hot-1:9200"]`, `username: elastic`, `password: ${ES_PASSWORD}`, `ssl.certificate_authority: /usr/share/filebeat/certs/ca.crt`, `index: "self-monitoring"`.
- `setup.ilm.enabled: false`, `setup.template.enabled: false` (managed by `setup`).
- Container: `user: root`, mounts `/var/lib/docker/containers` (ro), `/var/run/docker.sock`, `ca.crt`; `command: filebeat -e -strict.perms=false`.

macOS note: `/var/lib/docker/containers` is accessible on Docker Desktop (shared Linux VM filesystem), so autodiscover works unmodified.

## 9. Rubric mapping

| Rubric requirement | Delivered by |
|---|---|
| Config files (ES, Kibana, shipper) | `config/`, `filebeat/`, `setup/` |
| Fault tolerance: survive 1 data-node loss | 3 masters + 2-per-tier + `replicas: 1` |
| ILM: Hot + Warm tiers | `policies/self-monitoring-policy.json` |
| ILM JSON export | same file; reproducible via `GET _ilm/policy/...` |
| Self-monitoring logs in `self-monitoring` index | Filebeat → `self-monitoring` alias |
| Screenshots of logs arriving | `docs/screenshots/` + README guide |

## 10. Resources & run flow

- ~16 GB free RAM recommended; Docker Desktop memory ≥ 16 GB. Heap values documented and adjustable for lighter machines.
- Disk: a few GB for ES data volumes during the demo.
- **Run flow:**
  1. `cp .env.example .env` (or edit the committed `.env`).
  2. `./setup/generate-certs.sh`
  3. `docker compose up -d` (setup auto-bootstraps).
  4. Open Kibana → login as `elastic`.
  5. Screenshots: Discover on data view `self-monitoring`; Stack Management → Index Lifecycle Policies; `GET _cat/indices/self-monitoring*` after a forced rollover showing a backing index on warm nodes.

## 11. Out of scope (YAGNI)

- Cold/frozen tiers (rubric needs only Hot + Warm).
- Metricbeat / cluster metric monitoring (rubric asks only for component logs → `self-monitoring`).
- Kubernetes / VM deployment.
- Logstash (Filebeat → ES directly is sufficient).
- Production hardening beyond demo (secret rotation, RBAC beyond built-in users).

## 12. Verified facts (sources)

- ES 9.4.4 is current GA (ES + Kibana must match). <https://www.elastic.co/docs/release-notes/elasticsearch>
- Standalone Beats still supported (~2027 EOL target); only Beats allow a single custom index name. <https://endoflife.date/beats>
- `node.roles` array, ILM API/actions, API-key API, `xpack.security.*` SSL settings — unchanged from 8.x. <https://www.elastic.co/guide/en/elasticsearch/reference/current/modules-node.html>
- Kibana uses `kibana_system` built-in user over HTTPS with `elasticsearch.ssl.certificateAuthorities`; password via `elasticsearch-reset-password -u kibana_system`. <https://www.elastic.co/guide/en/kibana/current/settings.html>
